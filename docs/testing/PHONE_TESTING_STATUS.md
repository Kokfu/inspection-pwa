## 1. The working loop

1. **Test** on the phone (or API/browser) → anything wrong becomes a row in §5 with an ID (`I-nn`), severity,
   how to reproduce and evidence.
2. **Fix** one issue (or a small related group) → add a regression test that **fails before / passes after**
   (prove it by temporarily restoring the original source with `git show HEAD:<file>`, never `git stash`).
3. **Rebuild** — the *user* rebuilds the Docker containers (the agent must not touch Docker Compose).
4. **Retest on the phone** with the same steps that found the issue; record before/after numbers.
5. **Update this file** (status column, test matrix, "Last updated"), then stop before staging. The user does git.

Severity: **P0** data loss/security hole · **P1** blocks core field work · **P2** degraded/confusing/hardening ·
**P3** cosmetic/cleanup. A task is not complete with an open P0/P1 in its scope (see `AGENTS.md`).

## 3. Environment and how to run things

### Running the phone tests
Tooling lives in `scripts/phone-testing/` (PowerShell + Node, no secrets). Start with:

```powershell
. .\scripts\phone-testing\phone-env.ps1
Initialize-PhoneEnv          # adb forward 9222, adb reverse 8081, starts proxy.js
Invoke-Cdp "location.hash"   # run JS in the phone's Chrome tab (prefix with @ to run a file)
```

How the phone reaches the app: `phone localhost:8081 → adb reverse → proxy.js → https://localhost (Caddy)`.
Caddy redirects plain HTTP to `https://localhost/` and the phone cannot bind ports < 1024, so the proxy exists purely
to give Chrome a secure-context `http://localhost` origin (service worker, IndexedDB, camera all work).

| To simulate | Do |
|---|---|
| **Truly offline** | `Set-PhoneOffline` (Wi-Fi off **and** proxy stopped — the USB tunnel works with Wi-Fi off, so the proxy must die too) |
| **Server unreachable, Wi-Fi up** | `Set-ServerUnreachable` |
| **API down behind Caddy (502/504)** | `docker stop inspection_pwa-api-1` … `docker start inspection_pwa-api-1` |
| Lost response / cut upload / slow / fake 401 | `Set-ProxyMode "dropresp:sync"`, `"cutreq:/api/v7-evidence/stage"`, `"slow:20000:sync"`, `"status:401:/api/sync"` |
| Force-close | `Stop-AppOnPhone` then `Start-AppOnPhone` |
| Back online | `Set-PhoneOnline` |

Other scripts: `mkVisit.js` (create a visit), `fillSmoke.js` / `fillIntercom.js` (fill + submit a record),
`intercomPhotos.template.js` (Not Good rows + photos, optional tamper), `state.js` (IndexedDB queue summary),
`timeline.js` (request/state timeline when opening a draft), `audit*.js` (mobile UI audit; `audit3.js` is the current one: define `window.__audit(name)` once, then call it per screen), `mkVisitAll.js` (visit with every system), `validate.js` (photo validation),
`authmatrix.ps1` (needs `PWA_*_USER/PASS` env vars), `relcheck.ps1` (does the deployed bundle contain the fix?), `pwfail.ps1` (group Playwright failures).
`state.js`/`orphans.js` hard-code the technician's per-user IndexedDB name `inspection-pwa:user:436`.

### Verify a rebuild reached the phone
1. `scripts\phone-testing\relcheck.ps1` — shows the active release, whether fix strings are in the bundle, and the build id.
2. On the phone: reload → "New version available" banner → **Update now** → build id in the header must change.

### Accounts
Demo logins (technician, supervisor, admin) are **not** stored in the repo or in this file. Ask the owner for them at the
start of a chat. Another technician (`Technician1`) owns SV-47/-48/-49; the app deliberately hides other technicians' jobs.

### Gotchas that cost time
- **Keyboard (Pinyin IME):** `adb shell input text` leaves text as an uncommitted suggestion → send `KEYCODE_SPACE` to commit; use alphanumerics (underscores get mangled).
- **Floating overlay bubble** (black/white circle on the left edge) makes Android refuse permission dialogs ("close any bubbles or overlays") → close it before testing the camera.
- **Screenshots:** use `Get-PhoneScreenshot` (`adb exec-out`). Saving PNGs on the phone gets them indexed into the gallery and shifts the photo picker.
- **Background Chrome tabs are frozen** — scripted control of a non-foreground tab hangs.
- `adb reverse` is lost when the adb server restarts → re-run `Initialize-PhoneEnv`.
- App data lives in a **per-user** IndexedDB (`inspection-pwa:user:<id>`); a test harness must seed it *after* login.
- Scripted HTTPS calls need Caddy's local cert accepted, and session cookies are `Secure` (use `https://localhost/api`, not the http proxy).
- A job's systems must be opened **online once** before they can be opened offline (see I-02).
- The Playwright baseline is now **179 pass / 0 fail**; any failure is new. Run time ~4 min when nothing times out.

### I-21 design brief — correcting a rejected photo record (decided 2026-10-08: option C, implemented for all systems)

**Why records get stuck (facts from the code).**
- Server: `staged_inspection_evidence` has `status IN ('staged','accepted')`, `photo_uuid` PRIMARY KEY and an unconditional `UNIQUE (inspection_client_uuid, system_key, field_path)` (migration 017). Staging is idempotent on `photoUuid` + fingerprint: same bytes → `duplicate`; different bytes for that `photoUuid` → `409 IDEMPOTENCY_CONFLICT`; a different `photoUuid` for an occupied field → `409 EVIDENCE_FIELD_OCCUPIED`. There is **no release/replace/delete** for staged evidence. Acceptance (`*V7Acceptance.ts`) requires the staged set for that `inspectionClientUuid` to equal the frozen manifest exactly (no missing, **no extra**), and rejects bytes already *accepted* elsewhere in the same Job+system (`EVIDENCE_CONFLICT`).
- Client: *Edit Failed Inspection* returns the **same** `clientUuid` to Draft. The photo save (`save<System>V7Photo`) happily **replaces the bytes but reuses the same `photoUuid`** (`existing?.photoUuid`), and Submit re-freezes the manifest from the new bytes. The skill says "the evidence set cannot change" on a correction, but no repository transaction enforces it — so the UI offers a replacement that the server must refuse (SV-59), and a record whose staged set no longer matches (SV-50) can never match again.
- Realistic triggers: the same image used at two locations / two devices of one Job+system (`EVIDENCE_CONFLICT`, cannot be detected offline across devices), a photo staged but the parent lost/rewritten, or any future evidence-related rejection. Non-evidence rejections (validation of the responses) already correct fine on the same UUID.

**Options**

| | What changes | Server / schema | Pros | Cons / risk |
|---|---|---|---|---|
| **C. Corrected copy (recommended)** | On a `Failed`/`Conflict` record add **"Start corrected copy"**: creates a **new record** (new `clientUuid`, new `photoUuid`s, same responses and photo bytes, which the technician may replace), re-freezes a fresh manifest, and retires the failed one locally (outbox marked Completed "Superseded by technician correction", local row set to a terminal `Voided/Superseded` state; its unique `jobSystemKey` freed). The old same-UUID *Edit Failed* stays for non-evidence rejections but **locks the photos** (enforces the skill rule) with a pointer to "Start corrected copy". | **None** (no migration, no API change). The rejected record was never accepted, so evidence uniqueness (accepted-only) is unaffected. | Smallest and safest; honours "frozen evidence is immutable"; works offline; no protected scope. Fixes both SV-50 and SV-59 shapes. | Orphaned `staged` rows for the dead UUID stay on the server (harmless, never accepted; later housekeeping can expire them — `expires_at` exists). Needs per-system wiring (11 repositories: intercom, hydrant, hose reel, sprinkler, dry/wet riser, smoke, roller shutter, fire alarm, CO2, FM200, wet chemical) behind one shared helper; Level-2 tests. |
| A. Re-key + supersede on the server | Replacing a photo on a correction Draft mints a new `photoUuid`; server adds `status='superseded'`, makes the field-unique index partial (`WHERE status='staged'`) and lets the same actor supersede staged evidence while the parent is unaccepted. | **Migration** (status CHECK + unique index) — protected scope; V6/V7 contract change. | Same record keeps its UUID. | Touches the evidence contract and every `*V7Acceptance`; larger blast radius; still no answer for SV-50's *extra staged* evidence unless supersede-all is also added. |
| B. Server "release evidence" + supervised discard | New endpoint to release staged evidence for an unaccepted record, plus a supervisor **void** of a Failed record. | Migration + new authenticated routes + audit. | Also gives managers a clean way to clear debris. | Biggest: new authority surface (backend-api-security), void semantics for reports. |
| D. Do nothing | Treat evidence rejections as terminal; purge debris manually. | None | Zero risk. | A technician with a rejected photo record has no recovery in the field. |

**Recommendation: C**, delivered in phases: (1) shared `startCorrectedCopy` core + lock photo replacement on same-UUID corrections, with Fire Intercom as the pilot (browser harness + Node tests that fail before / pass after, incl. offline, exact-UUID sync of the new record, old record never re-sent); (2) roll out to the other systems one at a time; (3) optional server housekeeping for expired never-accepted staged rows. No migration is needed for any phase.

**Questions for the owner**
1. Is a corrected copy acceptable (the failed record disappears from the job as `Superseded`, the new one carries the work), or must the original UUID be preserved?
2. May a technician replace *any* photo in a corrected copy, or only those whose evidence was rejected?
3. Should supervisors/managers also see superseded rejected records (audit), or only the technician's device?
4. Roll out to all 11 systems in one task, or pilot on Fire Intercom first (recommended)?

- The proxy image carries the web build. After source changes use `docker compose build --no-cache proxy; docker compose up -d proxy`; a plain `up -d --build` once reused a stale layer.
