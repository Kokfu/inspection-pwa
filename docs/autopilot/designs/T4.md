# T4 — Supervisor role (design)

Status: **NEEDS OWNER** — write `APPROVED` (optionally with answers to §8) at the end of this file.
Branch `claude/autopilot`, base `7a53735`. Read with `backend-api-security` and `offline-first-pwa`.

## 1. Problem

The owner decision (2026-09-19) is that a **supervisor reviews submitted inspections, makes audited
corrections and approves reports**. A supervisor **cannot** manage users, customers, templates or
configuration. The admin (manager) keeps everything and can also do everything a supervisor can.

Today there are only two roles: `users.role CHECK (role IN ('admin','inspector'))`
(`apps/api/migrations/002_auth_security_foundation.sql:5`). `UserRole = "admin" | "inspector"`
(`apps/api/src/auth/authTypes.ts:1`), and `requireRole(...roles)` is an exact-match list
(`apps/api/src/middleware/requireRole.ts:4`). T4 adds the role and read access for review. T5
(corrections) and T6 (approval) build on it later, each with its own design.

## 2. Options

**A. A new `supervisor` role and explicit route lists (recommended).** Add `supervisor` to the CHECK and
to `UserRole`. Every route keeps an explicit `requireRole(...)` list. Review routes list
`"admin", "supervisor"`, and configuration routes stay `"admin"` only. There is no role hierarchy
inside `requireRole`, so each route shows exactly who may call it.

**B. A hierarchy in `requireRole` (admin ⊇ supervisor ⊇ …).** Fewer edits, but every current
`requireRole("admin")` would silently need to decide whether a supervisor passes. With
`requireRole("admin", "inspector")` routes in the mix, one mistake grants inspector-level write paths
(sync, staged evidence) to supervisors. Rejected: implicit authority is the failure mode
`backend-api-security` warns about.

**C. A permission table (role → permission rows).** Most flexible, but a new schema and a UI to manage
it. More than a 3-role product needs. Rejected for now; A can move to C later without a data
migration.

## 3. Recommendation (option A) in detail

### 3.1 Data / migration
New forward-only migration `apps/api/migrations/031_supervisor_role.sql`. No applied migration is
edited.
```sql
ALTER TABLE users DROP CONSTRAINT IF EXISTS users_role_check;
ALTER TABLE users ADD CONSTRAINT users_role_check
  CHECK (role IN ('admin', 'inspector', 'supervisor'));
```
(`users_role_check` is PostgreSQL's generated name for the inline CHECK in 002; the implementation
first asserts that name in the integration test so a mismatch fails loudly instead of leaving two
constraints.) Existing rows are unchanged. There is no backfill. Rollback is possible only while no
supervisor rows exist (re-add the two-value CHECK).

### 3.2 API authority (`requireRole` semantics unchanged; lists change)

| Route (today `admin` only unless noted) | Supervisor | Why |
|---|---|---|
| `GET /manager/service-visits`, `GET /manager/service-visits/:jobId` | **yes** | review list / detail |
| `GET /manager/service-visits/:jobId/final-report(.pdf)` | **yes** | review + later approval (T6) |
| Services Done / technician visit history (`managerServiceVisits` history reads) | **yes** | review |
| Accepted detail `masterSystemInspections` GETs (today `admin,inspector` with inspector ownership filter) | **yes, all jobs** (treated like admin in the ownership filter, read-only) | review |
| `GET /manager/technicians` | **read-only yes** | the Services Done technician filter needs names |
| `POST /manager/technicians`, `…/deactivate` | no | user management |
| `GET /manager/customers` (list) | **read-only yes** (see §8 Q1) | the Services Done customer search needs it |
| `GET /manager/customers/:id` and every `configuration`, `label-overrides`, `system-configuration`, `evidence-policy`, `locations`, `contact-details`, `next-service-due-date`, `upcoming-service`, POST/PUT | no | customer/config management |
| Technician write paths: `sync`, `stagedEvidence`, `inspectionAttachments` POST, `inspectionJobs` create | no | a supervisor does not perform inspections |

`technicianOwns` (`apps/api/src/jobs/technicianOwnership.ts:14`) and `ownedMultipart.ts:14` short-circuit
for `admin`. They will **not** gain a supervisor short-circuit. Supervisor reads use dedicated read-only
queries (or the existing Manager read routes), so no inspector write path ever accepts a supervisor.
The creator-snapshot validators in sync (`role === "admin" || "inspector"`) stay unchanged, because a
supervisor never submits.

### 3.3 Creating a supervisor
Extend the existing admin-only create-technician form and `POST /manager/technicians` with an optional
`role: "inspector" | "supervisor"` (default `inspector`, so today's clients are unchanged). Deactivate
works the same for both roles (`WHERE role IN ('inspector','supervisor')`). Never hard-delete. The
Technician List shows a Role column. Only an admin can create or deactivate. A supervisor gets 403.

### 3.4 Web experience
- `productRoleMatches`: the "Manager" presentation accepts `admin` **or** `supervisor`. "Technician"
  stays `inspector` only.
- A supervisor sees Manager Home with only: **Services** (operations list, read-only),
  **Current Services Done**, and the visit detail / Final Report / accepted detail screens. Hidden:
  Technician List management, Add Customer, customer configuration, Next Upcoming Service, and the
  per-service editor. The routes are also guarded client-side (a supervisor deep-linking to
  `#/manager-customer/…` is sent to Manager Home), and the server 403 remains the authority.
- The T3 remembered choice also applies to a verified supervisor. The owner stamp is unchanged.
- Offline: unchanged. The Manager experience (and so the supervisor's) is server-backed only and never
  unlocks from a cached identity.

### 3.5 Audit
Use the existing `audit_events` table (`auditLog()`), with no schema change:
- `user.create` / `user.deactivate`, with `entity_type='user'`, `entity_id=<id>` and `reason='role=supervisor'`
  when a supervisor account is created (the technician paths already audit creation; the role is added to
  the reason).
- `authz.denied` for each supervisor 403 on a Manager route (`result='failure'`,
  `reason='<method> <route pattern>'`). This makes misuse visible without logging request bodies.
- Corrections and approvals are audited in T5/T6, not here.

## 4. Data / migration impact
- One additive migration (031). No existing row changes, and no applied migration is touched.
- Historical immutability is unaffected: templates V1–V7, accepted inspections, evidence and manifests
  are not touched.
- The runtime DB gets 031 only through the normal deploy path (owner). Tests use the disposable DB only.

## 5. Offline impact
None for technicians. Supervisors, like managers, have no offline authority. An offline supervisor sees
the existing "Reconnect to verify Manager access" message.

## 6. Test plan
- **API integration (disposable DB):**
  - migration 031 applies and is idempotent;
  - the constraint name is asserted;
  - a supervisor user can be inserted and an unknown role is still rejected;
  - admin creates a supervisor (and an inspector with no `role` field still works);
  - a supervisor cannot create or deactivate users (403 + `authz.denied` audit row);
  - a supervisor can call every "yes" route in §3.2 and gets 403 on every "no" route (table-driven,
    so each new Manager route must be classified);
  - a supervisor sees accepted detail for any job;
  - a supervisor cannot sync, stage evidence or create a job.
- **Unit:** `productRoleMatches` truth table (admin / supervisor / inspector × Manager / Technician).
- **Playwright:**
  - a supervisor reaches Manager Home with only the allowed cards;
  - a deep link to customer configuration redirects to Home;
  - Services Done and the Final Report work;
  - the admin create form offers the Role choice;
  - T3 reload restore works for a supervisor.
- **Revert proofs:** remove the supervisor entry from one "no" route's guard → the table test fails;
  remove the client-side guard → the deep-link spec fails.
- **Gates:** `Test-ManagerScheduling.ps1` plus the standard API gates (API + auth change).

## 7. Out of scope (later tasks)
Corrections (T5), report approval (T6), the daily access code (T11), and any PDF/report rendering files.

## 8. Questions for the owner (recommendation first)
1. **Customer list for supervisors.** Services Done needs to search customers. Recommendation: a
   supervisor may **read** the customer list (names and codes only, via the existing list route) but no
   customer detail or configuration. Alternative: a dedicated minimal `GET /manager/review/customers`.
2. **Next Upcoming Service.** Recommendation: **hidden** for supervisors (it edits due dates). If they
   should see it, it would be read-only.
3. **Name in the UI.** Recommendation: "Supervisor" for the role label, with the chooser card still
   "Manager" (the same experience, fewer cards).
