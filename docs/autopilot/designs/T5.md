# T5 — Supervisor corrections with version / audit (design)

Status: **NEEDS OWNER**. Write `APPROVED` (with answers to §9) at the end of this file.
Branch `claude/autopilot`, base `97dcd8a`. Read with `v7-evidence-acceptance`, `backend-api-security`
and `offline-first-pwa`. T4 (supervisor role) is done. This task also carries T4's deferred item:
supervisor read access to accepted detail and evidence photos.

## 1. Problem

A supervisor (or admin) must be able to correct a mistake in a submitted inspection, for example a
result entered as Not Good that should be Good, or a mistyped reading or remark. Every correction must
record who made it, when, which field, the old value, the new value and why.

**Hard constraint:** an Accepted inspection is immutable forever (`v7-evidence-acceptance`, "Atomic
Acceptance" §4). The Final Report / PDF may be built only from the accepted authority chain. So a
correction can never be an `UPDATE` of `master_system_form_instances.response_payload`. It has to be
an additive, versioned record that points at the accepted authority.

## 2. Options

**A. Append-only correction records per field (recommended).**
- A new table stores one row per corrected field: the accepted form instance, the field path, the value
  it replaces, the new value, the reason, the actor and the time.
- The *effective* value of a field is the accepted value with that field's latest correction applied.
- The accepted row is never touched. The original stays readable forever, and the full history is the
  list of rows in order.

**B. Versioned full snapshots.**
- Each correction set stores a complete corrected copy of `response_payload`.
- Simple to read, but field-level "old → new" has to be diffed back out.
- It duplicates large payloads, and it makes concurrent edits of different fields conflict needlessly.
- Rejected.

**C. Overlay JSON patch per inspection (one mutable row).**
- Violates "append-only" (the patch row itself would be updated), so the history would need a second
  table anyway.
- Rejected.

## 3. Recommendation (option A) in detail

### 3.1 Data (new forward migration `032_inspection_corrections.sql`)

```sql
CREATE TABLE inspection_corrections (
  id               UUID PRIMARY KEY,
  form_instance_id UUID NOT NULL REFERENCES master_system_form_instances(id),
  job_id           UUID NOT NULL REFERENCES inspection_jobs(id),
  system_key       TEXT NOT NULL,
  field_path       TEXT NOT NULL CHECK (length(field_path) BETWEEN 1 AND 300),
  sequence         INTEGER NOT NULL CHECK (sequence >= 1),   -- per (form_instance_id, field_path)
  previous_value   JSONB NOT NULL,       -- the value this row replaces (accepted value, or the prior correction's new_value)
  new_value        JSONB NOT NULL,
  reason           TEXT NOT NULL CHECK (length(btrim(reason)) BETWEEN 3 AND 500),
  corrected_by_user_id BIGINT NOT NULL REFERENCES users(id),
  corrected_by_role    TEXT NOT NULL CHECK (corrected_by_role IN ('admin','supervisor')),
  corrected_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  request_id       UUID NOT NULL UNIQUE,  -- idempotent retry of the same submission
  UNIQUE (form_instance_id, field_path, sequence)
);
-- Append-only: a trigger raises on UPDATE and DELETE of inspection_corrections.
```

- The column types follow the real ones (`master_system_form_instances.id` is a UUID).
- The implementation re-checks every FK type against the live schema before writing 032.
- Existing tables are unchanged. No backfill, and no migration of accepted data.

### 3.2 What can be corrected

- **Records:** V7 accepted records only (see §9 Q1). V1–V6 stay read-only.
- **Fields:** checklist results (the 4-state `good` / `not_good` / `complete_repair` / `na`), remarks,
  measurement readings and free-text fields (control-panel location, comments, row
  location/zone text). The field paths are the same scheme the label overrides already use
  (`collectResolvedLabelPaths`), plus the value leaf (`.result`, `.remarks`, `.values.<key>`).
- **Validation:** each new value is checked against the **frozen** contract of that record
  (`displayControls` / template snapshot): allowed result options, text length and number format. It
  is never checked against the current template.
- **Not correctable:**
  - evidence photos (the bound accepted photos never change);
  - job, customer, site, location identity;
  - creator, times and sync metadata;
  - `Normal` / `Test` / `Isolation` detector states (a separate control; see §9 Q2);
  - adding or removing repeatable rows.
- **Evidence rule:** correcting a result *away from* Not Good leaves its bound photo attached, shown as
  "evidence captured for the original result". Correcting *to* Not Good does **not** require a new photo
  (there is no photo path for a supervisor). The report shows "no photo — corrected by supervisor"
  instead. See §9 Q3.

### 3.3 API

| Route | Roles | Notes |
|---|---|---|
| `GET` accepted-detail routes (`masterSystemInspections` GETs) | admin, inspector (own), **supervisor (all)** | T4 carry-over; each response adds `corrections: [...]` and `effectiveResponses` (see 3.4) |
| `GET` accepted evidence photo routes (`inspection-attachments/:id/content`, `v6-evidence/accepted/...`, `v7-evidence/accepted/...`) | admin, inspector (own), **supervisor (all, read-only)** | T4 carry-over |
| `POST /manager/inspections/:clientUuid/corrections` | admin, supervisor | body `{ requestId, reason, changes: [{ fieldPath, expectedCurrentValue, newValue }] }` |
| `GET /manager/service-visits/:jobId/corrections` | admin, supervisor | a flat list for the review screen and the report notice |

POST semantics:
- **One transaction.** Lock the accepted instance row `FOR SHARE`. For each change, compare
  `expectedCurrentValue` with the current effective value (optimistic concurrency, so a stale screen
  gets `409 CORRECTION_CONFLICT` and nothing is written). Validate `newValue` against the frozen
  contract. Insert one row per change with the next `sequence` for that path. Write an `audit_events`
  row per change: `action='inspection.correct'`, `entity_type='form_instance'`,
  `reason=<fieldPath>`. The reason text itself stays in the correction row, not in the audit log.
- **Idempotency.** A retry with the same `requestId` returns the same stored rows. The same
  `requestId` with a different body gets `409`.
- **Refusals** (all fail closed): a no-op change (`newValue` equals the current value) → `400`; a
  non-V7 record → `422 CORRECTION_NOT_SUPPORTED`; a Draft / Pending or unknown record → `404`.
- **Job state.** Corrections are allowed on open and closed jobs. Closing a job never blocks review.

The ownership code gains **no** supervisor short-circuit. The reads use an explicit "reviewer" branch
on those GET routes only. Inspector write paths (sync, staging, uploads) keep refusing supervisors, and
the T4 route matrix test is extended to classify the new routes.

### 3.4 How corrected values are shown

- **Accepted Detail (web):** every corrected field shows the effective value with a "Corrected" badge.
  Under it: "Originally: Not Good (technician-one, 18 Sep 10:00) · Corrected by review-lead, 20 Sep
  14:10: *reason*". Earlier corrections to the same field are listed underneath. The original is
  always visible.
- **Manager screens:**
  - The service-visit detail lists each accepted record per system and location, linking to its
    accepted detail. That is new: today the Manager UI has no path to accepted detail. A supervisor
    corrects from there, using the same inline edit pattern as the T1 wording editor with a required
    Reason field and the unsaved-changes guard.
  - Only supervisors and admins see the Correct action. Technicians see corrections read-only (§9 Q4).

### 3.5 Final Report / PDF (the PDF work owns these files; T5 does not edit them)

`apps/api/src/reports/**`, the R2/R3 renderer and PDF files belong to the PDF work. T5 delivers
the **input** that work will need, and the Manager web view notice below.

**View-model input for the PDF work (proposal):**
- `FinalReportField` gains `corrected?: { originalValue: string; correctedBy: string; correctedAt: string; reason: string }`.
- The value shown in `FinalReportField.value` is the *effective* value.
- `FinalServiceReport` gains `corrections: Array<{ systemKey; locationLabel; fieldLabel; originalValue; correctedValue; correctedBy; correctedAt; reason }>`
  for a "Corrections" appendix page.
- `deriveSystemCondition` runs on effective values.
- T5 ships a pure helper, `applyCorrections(responsePayload, corrections) → effectivePayload`, in a new
  file outside `reports/`, with unit tests. The report loader can call it, so both sides share one rule.

**Until the PDF work integrates this (see §9 Q5):**
- The Manager Final Report web view (`apps/web/src/manager/ManagerFinalReportView.tsx`, not a report
  file) shows a clear notice when the visit has corrections: "N corrections were made after submission
  — this report still shows the values as originally accepted", plus the corrections list.
- Recommendation: the Download PDF button is disabled for a corrected visit, with that notice, until
  the PDF work lands. A PDF that silently shows uncorrected values is worse than no PDF.
- The technician PDF route stays as it is. Technicians download their own visit's report today, and
  the same notice would apply (see §9 Q5).

### 3.6 Interaction with T6 (report approval)
- An approved report must not change underneath its approval. Recommendation for T6: a correction
  after approval moves the report back to "awaiting approval", with audit.
- T5 only exposes the correction list and a `latestCorrectionAt` value T6 can compare against.

## 4. Data / migration impact
- One additive migration (032): a new table plus an append-only trigger. No existing row changes.
- Historical immutability is intact:
  - accepted instances, evidence, manifests and templates are never written;
  - V1–V6 records are not correctable;
  - migrations 017* are untouched.
- Rollback is possible only while the table is empty. Once rows exist, they are audit history and must
  be kept.

## 5. Offline impact
- Corrections are online-only (Manager / supervisor experience).
- Technician devices keep their local accepted copy. When online, accepted detail comes from the
  server, including corrections.
- No IndexedDB schema change, no outbox change, and no effect on drafts or pending sync.

## 6. Security
- Supervisor reads widen to all accepted records and photos (read-only), which is the owner's review
  requirement. Every write path stays closed to supervisors.
- **Correction writes:**
  - only admin and supervisor may write, through the one new route;
  - the target is resolved server-side from `clientUuid` (never a client-supplied job, system or
    location);
  - `fieldPath` is validated against the frozen contract's path set (no arbitrary JSON path);
  - `newValue` is type-checked;
  - the reason is length-bounded;
  - there is no string-built SQL.
- **Existence oracle:** a record the actor may not see and a record that doesn't exist both return
  `404`.
- **Audit:** every correction row is itself the audit record, and `audit_events` carries a pointer
  (actor, action, field path) for the global log.

## 7. Test plan
- **Unit:**
  - `applyCorrections` (latest-wins per path, untouched paths, non-V7 refused);
  - frozen-contract validation per control type;
  - path whitelist.
- **API integration (disposable DB):**
  - migration 032 applies and replays;
  - UPDATE/DELETE on corrections raise;
  - supervisor and admin correct a V7 accepted Hose Reel and Fire Alarm record;
  - the accepted row is byte-identical afterwards (hash `response_payload` before and after);
  - a stale `expectedCurrentValue` gets 409 with nothing written;
  - `requestId` idempotency;
  - a no-op change gets 400;
  - a V6 record gets 422;
  - an inspector gets 403 on POST;
  - a technician sees corrections on own records only;
  - the supervisor reads accepted detail and photos for any job;
  - the T4 route matrix is extended with the new routes.
- **Playwright:**
  - the supervisor corrects a result with a reason, and the badge and the original show;
  - the unsaved-changes guard works;
  - the Final Report view shows the notice and the corrections list;
  - the PDF button behaves per §9 Q5;
  - a technician sees corrections read-only.
- **Revert proofs:**
  - drop the append-only trigger → the UPDATE test fails;
  - skip the concurrency check → the stale-edit test fails;
  - allow a non-whitelisted path → the path test fails.
- **Gates:** `Test-ManagerScheduling.ps1` plus the standard V7 integration set (accepted-detail
  routes change).

## 8. Out of scope
- Photo replacement or new evidence by a supervisor.
- Correcting V1–V6 records.
- Adding or removing repeatable rows.
- Editing report or PDF files (PDF work).
- Report approval (T6).

## 9. Questions for the owner (recommendation first)
1. **Which records.** Recommendation: **V7 records only**. Older V1–V6 records stay read-only.
2. **Detector N/T/I states** (Normal/Test/Isolation). Recommendation: **not correctable** in T5.
   They are a separate control whose semantics must never change. Correcting them later needs its own
   design.
3. **Correcting a result to Not Good without a photo.** Recommendation: **allowed**, shown as
   "no photo — corrected by supervisor". The alternative is to forbid corrections to Not Good.
4. **Technicians see corrections to their own records?** Recommendation: **yes, read-only** (effective
   value plus original, who corrected it and why).
5. **Reports before the PDF work integrates corrections.** Recommendation: the Manager web report shows
   the corrections notice and list, and **PDF download is disabled for corrected visits** (Manager and
   technician) until the PDF work ships the corrected report. The alternative is to allow the PDF with
   the web notice only.
6. **Reason.** Recommendation: **mandatory**, 3–500 characters, free text.
