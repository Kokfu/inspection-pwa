# T6 — Report approval (design)

Status: **NEEDS OWNER**. Write `APPROVED` (with answers to §8) at the end of this file.
Branch `claude/autopilot`, base `71303d3`. Read with `backend-api-security` and `v7-evidence-acceptance`.
Prerequisite T4 (supervisor role) is DONE; T5a–T5c (corrections) are DONE.

## 1. Problem

A completed service visit's report should move from **awaiting approval** to **approved**, by an admin or
a supervisor, with an audit trail. Today a visit has only `status open | closed`
(`apps/api/src/jobs/jobCompletion.ts:414`): closing it makes the Final Report available immediately, and
nobody signs it off.

Two things the backlog asks this design to settle: whether technicians see the state, and whether an
unapproved report can be downloaded.

## 2. Options

**A. Append-only approval events + derived state (recommended).**
A new table records one row per decision (approve / withdraw) for a job. The report's state is derived:
the latest event wins, and a correction recorded after the latest approval puts the visit back to
awaiting approval. Nothing is overwritten, so "who approved this, when, and what happened next" is
answerable forever — the same shape as T5 corrections, and the same shape auditors expect.

**B. Columns on `inspection_jobs` (`report_status`, `approved_by`, `approved_at`).**
One `UPDATE` per decision, simplest reads. But it overwrites history: an approval that was withdrawn, or
re-approval after a correction, leaves no trace beyond `audit_events` prose. Rejected — approval is
exactly the fact a client may dispute later.

**C. Reuse `audit_events` as the store.**
No new table, but `audit_events` is a flat log with no constraints, no uniqueness and no FK to the job;
deriving state from it means parsing `reason` strings. Rejected.

## 3. Recommendation (option A)

### 3.1 Data — new forward migration `033_report_approvals.sql`

```sql
CREATE TABLE report_approvals (
  id UUID PRIMARY KEY,
  job_id UUID NOT NULL REFERENCES inspection_jobs(id) ON DELETE RESTRICT,
  decision TEXT NOT NULL CHECK (decision IN ('approved', 'withdrawn')),
  note TEXT CHECK (note IS NULL OR length(btrim(note)) BETWEEN 3 AND 500),
  decided_by_user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  decided_by_role TEXT NOT NULL CHECK (decided_by_role IN ('admin', 'supervisor')),
  decided_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  sequence INTEGER NOT NULL CHECK (sequence >= 1),
  request_id UUID NOT NULL,
  UNIQUE (job_id, sequence)
);
CREATE INDEX idx_report_approvals_job ON report_approvals (job_id);
-- Append-only, like inspection_corrections: a trigger refuses UPDATE, DELETE and TRUNCATE.
```

`withdrawn` exists only if the owner answers §8 Q1 "yes"; otherwise the CHECK lists `'approved'` alone.

### 3.2 Derived state (one function, used by every route)

```
reportApproval(job) =
  job.status = 'open'                      -> "not_applicable"   (no report yet)
  no approval events                       -> "awaiting_approval"
  latest event is 'withdrawn'              -> "awaiting_approval" (with who withdrew it and when)
  latest event is 'approved'
    and no correction after decided_at     -> "approved"
    and a correction after decided_at      -> "awaiting_approval" (reason: "corrected after approval")
```

The correction comparison uses `MAX(inspection_corrections.corrected_at)` for the job (T5a), which is why
T5 exposed it. One SQL helper returns `{ status, decidedBy, decidedByRole, decidedAt, note,
latestCorrectionAt, correctedAfterApproval }`; every consumer uses it so the Manager list, the visit
detail, the report view and the PDF gate can never disagree.

### 3.3 API

| Route | Roles | Notes |
|---|---|---|
| `POST /manager/service-visits/:jobId/report-approval` | admin, supervisor | `{ requestId, decision, note? }`; idempotent by `requestId`; `409` if the state moved under the caller (`expectedStatus` in the body) |
| `GET /manager/service-visits/:jobId/report-approval` | admin, supervisor | current state + the full event history |
| `GET /manager/service-visits` and `/:jobId` | admin, supervisor | gain an additive `reportApproval` summary (the web validators accept extra keys — checked) |
| `GET /inspection-jobs/:jobId/completion` | admin, inspector | gains the same summary only if §8 Q3 is "yes" |

Refusals fail closed: approving an open visit → `409 REPORT_NOT_READY`; a visit that does not exist or
is a sample → `404`; an inspector → `403` (they never approve); a note over 500 characters → `400`.

### 3.4 Download / visibility rules (see §8 Q4)

Recommended:
- **Viewing** the report on screen: unchanged for admin and supervisor (they must read it to approve it).
- **PDF download**: only when the state is `approved`. An unapproved visit returns
  `409 REPORT_NOT_APPROVED` on both PDF routes, next to T5a's existing
  `409 FINAL_REPORT_HAS_CORRECTIONS`. This makes "approved" the thing that lets a report leave the
  building, which is the point of the feature.
- **Technicians**: see the state read-only on their own visit (§8 Q3), and their PDF route follows the
  same rule.

### 3.5 Web

- **Manager Operations / Services Done**: a status chip per completed visit — "Awaiting approval" or
  "Approved <name>, <date>".
- **Final Report view**: an approval panel — current state, who decided and when, the note, and an
  **Approve report** button for admin and supervisor. After a correction lands the panel shows
  "corrected after approval — re-approval needed" and the button returns.
- **Manager Home**: an "Awaiting approval" count (shares the T7 reminder layout; T7 may land first).
- **Technician**: a read-only chip on their completed visit.
- Admin-only if §8 Q1 is yes: **Withdraw approval**, with a required note.

### 3.6 Interaction with T5 and the PDF work

- A correction after approval reverts the state (§3.2), so a corrected report can never stay signed off.
- T5a's PDF refusal for corrected visits stays; T6 adds a second refusal for unapproved ones. Once the
  PDF work renders corrections, only the approval gate remains.
- No report or PDF rendering file is touched; the gates live in the route handlers as T5a's does.

## 4. Data / migration impact
One additive migration (033). No existing rows change. A visit closed before T6 ships simply has no
events, so it reads as awaiting approval — which is true.

## 5. Offline impact
None. Approval is a Manager/supervisor action, online only. Technicians read a state that arrives with
the visit; nothing is cached for offline decisions, and no sync payload changes.

## 6. Security
- Only admin and supervisor may POST; the route is audited (`report.approve` / `report.withdraw`) and
  goes through `requireRoleAudited`, so a refused supervisor leaves an `authz.denied` row.
- The decision records the actor's role at the time, so a later role change cannot rewrite history.
- `expectedStatus` + `requestId` prevent a double-click or a stale screen from approving twice.
- The PDF gate is applied after the existing access check, so it cannot become an existence oracle.

## 7. Test plan
- **Unit**: the derived-state function (no events; approved; withdrawn; approved-then-corrected;
  open job), and its ordering under same-millisecond timestamps.
- **API integration (disposable DB)**: migration 033 applies and replays; append-only triggers; approve
  → state approved + audit row; approve twice with the same `requestId` → idempotent; with a stale
  `expectedStatus` → 409; an inspector → 403; an open visit → 409; a correction after approval flips the
  state back and the PDF is refused again; the closed route matrix (T4) classifies both new routes.
- **Playwright**: a supervisor approves from the Final Report and the chip updates; a correction after
  approval shows "re-approval needed"; a technician sees the chip read-only (Q3); PDF disabled while
  unapproved.
- **Revert proofs**: remove the approval gate on the PDF route → the download test fails; remove the
  correction check from the derived state → the re-approval test fails; drop the append-only trigger →
  the UPDATE test fails.
- **Gates**: `Test-ManagerScheduling.ps1` plus the standard API gates.

## 8. Questions for the owner (recommendation first)
1. **Can an approval be withdrawn?** Recommendation: **yes, admin only, with a required note.** A
   supervisor approves; only an admin can reverse it.
2. **Does a correction after approval require re-approval?** Recommendation: **yes** — otherwise a
   signed-off report can change underneath the signature.
3. **Do technicians see the approval state?** Recommendation: **yes, read-only, on their own visits.**
   They learn that their work has been accepted without gaining any control over it.
4. **Can an unapproved report be downloaded as PDF?** Recommendation: **no** — approval is what releases
   the report. Viewing on screen stays open to admin and supervisor.
5. **Is approval per visit or per system?** Recommendation: **per visit** — the report is one document.
6. **Who approves in practice — supervisor, admin, or either?** Recommendation: **either**, matching the
   2026-09-19 decision that a supervisor approves reports and an admin can do anything a supervisor can.
